## Что установлено по исходникам

```text
Существующий web UI (video_descriptor.serve, порт по умолчанию 8000)
  → загрузка в data/uploads → файловая очередь output/jobs
  → ffmpeg: моно PCM16 WAV 16 кГц
  → Whisper small: HTTP Windows NPU, профиль 8766
  → pyannote community-1: отдельный Python/PyTorch XPU для диаризации
  → назначение говорящих и сохранение speech.json
  → перевод через Ollama/Qwen или Gemini по настройкам
  → web-редактор, отчёты, субтитры
```

В проекте также есть OCR (Tesseract), обработка кадров (OpenCV), конспекты и
другие движки речи. Наличие кода не означает, что вся цепочка проверена на Windows.
В `serve.py` уже есть страницы создания, API очереди и редактора, экспорт VTT/текста.
Полный аудит экспорта SRT ещё не выполнен.

Конкретные препятствия нативному запуску:

1. `jobs.py` и `speech_resume.py` импортируют Unix-модуль `fcntl`.
2. `jobs.pipeline_busy()` читает `/proc`; в Windows этот каталог отсутствует.
3. `jobs.run_job()` ищет `.venv-diarization[-xpu]/bin/python` и предлагает bash-скрипт.
   Нужны Windows-пути и проверка реального окружения диаризации.
4. В нескольких модулях адрес по умолчанию — `host.docker.internal`.
   Для нативного процесса нужны явные `127.0.0.1:11434` и `127.0.0.1:8766`.
   Старый `.devcontainer/runtime.env` указывает ещё на английский сервис 8765.
5. Сохранённые манифесты, задания и ключи кэша используют абсолютные Linux-пути.
   Простая замена текста может нарушить идентичность кэша; нужна отдельная миграция.
6. Глобальный Windows Python 3.12.10 есть, но зависимости основного приложения
   в нём не установлены. В текущем PATH не найдены ffmpeg/ffprobe/tesseract.
   Это не доказывает их отсутствие на диске.

Docker API был недоступен при проверке. Сервисы не запускались и не останавливались.

## Архитектурное направление и объём

Предлагается нативный Windows UI/координатор с отдельной `.venv` в этой папке,
существующий NPU HTTP-сервис и существующий Windows Ollama. Первый интерфейс —
уже имеющийся web UI, открываемый ярлыком; desktop-оболочку можно оценить позже.
До проверки PyTorch XPU + pyannote на Windows нельзя обещать полный отказ от
Linux для диаризации. При необходимости её можно временно оставить отдельным
WSL-процессом без devcontainer, но это также требует проверки окружения.

План до большой реализации:

1. Закончить точную карту конвейера, данных и API; исследование конкурентов и
   официальной поддержки оборудования из исходного задания пока не выполнено.
2. Проверить Windows XPU/pyannote отдельным небольшим probe, без изменения NPU-окружения
   и без автоматического скачивания моделей. Эта проверка определяет границу отказа от WSL.
3. Показать окончательное решение и уточнить оценку. Предварительно: небольшой
   нативный запускатель/UI и блокировки — 0.5–1 рабочий день; перенос старых путей,
   проверка диаризации и восстановления — ещё 1–3 дня, в зависимости от совместимости.
   Это ориентир по коду, не результат проверки оборудования.
4. После этого минимальный прототип: Windows-блокировки, запускатель с health-check,
   защита от второго экземпляра, явная конфигурация адресов, открытие UI и отдельные логи.
5. Проверить короткое/длинное видео, отсутствие речи, end_ts=-1, правку и экспорт,
   повторный запуск и восстановление. Лишь затем делать установку и обновление.
