# Качество Intel XPU: диагностика 20.10.2026

Причина **3 интервала CPU против 23 XPU** воспроизведена и изолирована:
`torch.nn.functional.one_hot` в PyTorch **2.14.1+xpu**, Arc 140V,
драйвер 32.0.101.8132 неверно обрабатывает singleton batch `[1, 589]`.
Это наблюдаемый дефект операции; конкретный внутренний kernel/driver не установлен.
Минимальный пример [не требует pyannote, модели или аудио](../scripts/repro_xpu_one_hot.py).
Он возвращает exit 1 при воспроизведении дефекта.

## Где возникает расхождение

Оба окружения используют один каталог community-1 revision
`3533c8cf8e369892e6b79ff1bf80f7b0286a54ee`, одинаковые параметры и PCM16/mono/16kHz.
Загрузчик делит PCM на 32768, добавляет размерность канала; resampling отсутствует.
Полные версии зависимостей и SHA256 всех файлов модели записаны в JSON.
Кроме CPU/XPU runtime различаются несколько сетевых/build пакетов; контроль CPU
**в том же XPU-окружении** также возвращает исходные 3 интервала.

На A SincNet/LSTM/classifier/log-softmax конечны, float32; максимальная разница
log probabilities — `4.86e-5`, argmax совпадает на всех кадрах. Первое существенное
расхождение — **powerset → multilabel**, внутри segmentation, до speaker counting,
embeddings, clustering и Annotation. One-hot содержит 522 ошибочных элемента;
число активных кадров падает с 376 до 34. Это теряет речь и создаёт 22 фрагмента
короче 50 мс. Annotation и конвертация приложения точно сохраняют эти границы.

Чистый Torch пример с `arange % 7` воспроизводит 522 неверные строки при
`[1,589]`, 523 при `[1,590]`; `[1,16]`, batch 2 и 32 проходят. Десятисекундное
окно segmentation на коротком A имеет batch=1; B имеет 51 полное окно, C — 171,
без отдельного singleton хвоста. Поэтому старый 60-секундный тест ошибку не выявил.
Неполный хвост длинной записи тоже может вызвать этот путь.

Операция должна возвращать ровно одну единицу на строку согласно
[контракту PyTorch](https://docs.pytorch.org/docs/2.14/generated/torch.nn.functional.one_hot.html).
Исследован установленный `pyannote/audio/utils/powerset.py` версии 4.0.7:
hard conversion = argmax → one_hot → matmul с powerset mapping.

## Исправление и Auto

После `pipeline.to(xpu)` worker оборачивает **только** upstream Powerset conversion:
scores и mapping переводятся на CPU. Используется исходная функция pyannote,
включая soft/overlap semantics. Её результат и прежде сразу копировался в NumPy/CPU.
SincNet, LSTM, classifier и embedding реально исполняются на `xpu:0` — сохранены
forward-hook device/dtype/shape. Clustering и Annotation остаются обычными CPU этапами.
Не менялись веса, пороги, dtype нейросетей, таймкоды и фильтрация коротких реплик.
Неизвестный тип conversion выдаёт понятную ошибку совместимости, вместо скрытого CPU inference.

**Auto сохраняет XPU с этим обходом:** на A/B/C совпадают все полные интервалы
и speaker IDs с CPU, максимальная разница границ 0 секунд. Явный XPU не заменяется
на CPU. Без обхода рекомендовать эту конфигурацию XPU нельзя.

Время в секундах, одиночные запуски; load отдельно от inference, без импорта Python.

B повторно использует **тот же** PCM SHA256
`f001f7390817fa56c6df58995783af1e1f310dadfd21475e0797f2f8e84a9daf`.
До и после обхода обе Annotation CPU/XPU на B и C совпадают. Настоящий интервал
B `38,995344–39,012219` (16,875 мс) сохранён, короткие реплики не отсекаются.
[Таблица каждого интервала и его длительности](verification-diarization-intervals.md).
[Все 14 запусков, промежуточные метрики, окружения и эталон](verification-diarization-quality.json).

C — первые 180 секунд AMI ES2004a Mix-Headset. Загружены только эти 5,76 MB PCM;
веса не скачивались. [AMI](https://groups.inf.ed.ac.uk/ami/corpus/) публикует
сигналы и транскрипции по CC BY 4.0; attribution: AMI Meeting Corpus, Carletta et al.
Эталон only_words взят из [pyannote/AMI-diarization-setup](https://github.com/pyannote/AMI-diarization-setup),
его разметка происходит из ручных AMI annotations 1.6.2.

DER: `pyannote.metrics 4.2.0`, UEM `[0,180]`, collar **0**, overlap **включён**,
оптимальное взаимно однозначное Hungarian speaker mapping на всём фрагменте.
И CPU, и исходный/исправленный XPU имеют **14,4458% DER** для exclusive результата
приложения; ordinary overlapping Annotation — **13,9800%**. В эталоне 3 голоса,
в предсказании 2: пропуски 14,182 с, confusion 0,894 с, false alarm 1,934 с
при 117,75 speaker-seconds эталона. Это backend parity, **не идеальная точность**.
Для A/B эталона нет: DER и объективная точность не заявляются.

## Установленное Windows-приложение

Отдельный installer 0.8.0, реальный embedded Python и WebView2, существующий
managed XPU Python и community-1. Использован ранее полученный реальный ASR
встроенного `speech-check.mp4`; Whisper повторно не запускался.
«Определить говорящих» создало отдельную версию с 3 интервалами на XPU.
Ручная правка текста, ID и границы исходной реплики сохранились. Затем UI назначил
`unknown` вместо найденного speaker ID; после настоящего перезапуска backend
и desktop значение сохранилось, SRT/VTT содержали исправленный текст.
Полный worker proof и результат сохранены в JSON; [скриншот после рестарта](diarization-quality/installed-restarted.png).

ASR fixture содержит одну целую реплику: приложение назначает ей голос по
наибольшему пересечению и предупреждает о ручном разделении. Этот сценарий
подтверждает сохранность данных и интеграцию, а не точность многоголосого ASR.
Многоголосые интервалы проверены отдельно на B/C.

## Повторение и ограничения

Запускать [offline probe](../scripts/probe_diarization_quality.py) существующим
managed CPU/XPU Python: `--model EXISTING_MODEL --audio SAME_PCM.wav --device cpu|xpu
--output result.json`. Для исходного дефекта добавить `--unpatched-xpu`.
Для DER C добавить `--reference ES2004a.rttm --uri ES2004a`.
Probe сохраняет полные exclusive/ordinary интервалы и `.arrays` с этапами.
Аппаратная регрессия без весов: существующим XPU Python выполнить
`scripts/repro_xpu_one_hot.py --check-workaround` (6 hard/soft случаев, exit 0).
Операции установок/скачиваний в probe отсутствуют.

Проверены одна Arc 140V и закреплённые версии; три записи не сертифицируют все
драйверы/длины/языки. В pyannote embeddings есть предупреждение о std пустого
маскированного участка; конечные Annotation валидны, предупреждение также есть
на CPU и не является причиной one-hot дефекта. Upstream issue не публиковался;
приложен независимый воспроизводимый пример. Ollama/Gemini, NPU, Whisper,
пользовательские модели и настройки не изменялись. Релиз не публиковался.
