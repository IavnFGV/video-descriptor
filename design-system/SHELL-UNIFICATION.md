# Единая оболочка и навигация

Статус: **шаги 1–6 реализованы и локально проверены**. Ветка реализации:
`codex/workspace-tabs-visual-draft`. Накопленные Bootstrap-правки сохраняются.
Это отдельное изменение оболочки, не заявление о завершении визуального переноса.

## Причина

До объединения `video_descriptor/assets/desktop-shell.js` строил общий ряд меню, но переносил
часть команд из DOM страницы. `updates-check`, диалог обновлений и `stop` есть
в `windows-app/ui/index.html`, но отсутствуют в библиотеке и workspace. Ссылки
«Записи» выбираются по типу страницы, а не по серверу: `/#records` и `/output/`
могут открывать разные представления на одном Windows-сервере.
`recording.js` дополнительно меняет ссылку после `/health`; `studio.js` и оболочка
частично дублируют перенос контекста перехода. Страницы справки не подключают
общую шапку. Наличие DOM-элемента сейчас ошибочно выступает признаком возможности.

## Результат

- Одна общая шапка с одним описанием меню и команд, общей геометрией и клавиатурой.
- Одинаковый состав глобальных команд на всех полных страницах одного сервера.
- Один источник определения среды: Windows HTTP host, shared web или offline export.
  Проверка через существующий `/health`; новые backend endpoints не нужны.
- Windows: «Записи» ведут в `/#records`, «Новая запись» — в `/#new`, настройки и
  диагностика — в существующие hash-разделы. Shared web: библиотека `/output/`,
  создание `/create`; неподдерживаемые native-команды не показываются как рабочие.
- Обновления и завершение доступны на полных страницах Windows host независимо
  от места входа. Офлайн-отчёт не предлагает управление приложением.
- «Вид» подключает существующий контроллер только в открытой записи; это
  контекстное отличие, а не отдельная версия шапки.

Не входят: React/SPA, объединение всех экранов в один HTML, новые функции,
переписывание backend, изменение логики панелей меню «Вид», state owners,
редакторов, worker/NPU, моделей, версий/BUILD, публикация и merge.
Сохранённые отчёты не переписываются. Embedded-редактор остаётся без шапки.

## Последовательность

Каждый пункт реализуется целиком и получает короткую сводку. Промежуточная
сводка не закрывает пункт с известным выполнимым остатком. После видимых изменений
нужна пауза для ручного просмотра. Не редактировать параллельно одну рабочую копию.

### 1. Общая сборка оболочки

Разделить существующий `desktop-shell.js` на понятные ответственности:
определение среды, описание команд, построение шапки и навигация. Начать внутри
существующего модуля; отдельный небольшой модуль нужен только при реальном
разделении ответственности, не создавать framework или универсальную plugin-систему.

Один общий результат `/health` используется оболочкой и подключаемыми командами.
Сетевой сбой не превращает Windows-среду в подтверждённый shared web: показать
недоступность, сохранить безопасные ссылки и возможность повторить чтение.
Оболочка монтируется один раз; асинхронная готовность не дублирует шапку и listeners.
Сохраняются existing IDs, `desktop-shell-ready`, порядок инициализации и focus.

Реализация: `desktop-shell.js` публикует один результат `/health` для оболочки,
главной и записи; Windows, shared web, offline и недоступный сервер различаются
по ответу или протоколу. При ошибке в шапке доступны сообщение и повторная проверка.
Разметка по-прежнему определяет место монтирования, но не возможности сервера.
Чтение `/health` ограничено десятью секундами; повтор не создаёт вторую шапку.
Команды и переходы объединены в шагах 2–4. Edge визуальный проход выполнен,
технические результаты записаны в [отчёте Bootstrap](BOOTSTRAP-REVIEW.md);
старые сохранённые отчёты не переписываются.

### 2. Общие команды приложения

Вынести создание controls/диалога обновлений из главного HTML в общую оболочку.
Существующий update controller подключать на всех полных Windows-страницах;
прямое открытие `/create` или `/output/` не должно требовать предварительного входа
на главную. Сохранить `/api/updates`, `/api/updates/check`, `X-App-Instance`,
busy/error states, badge и открытие релиза через разрешённую команду host.
Обычный опрос читает локальное состояние; запрос GitHub не запускается навигацией.

Завершение использует прежний `/api/native/stop`, проверку instance и отказ 409
при активной работе. Не проверять его на действующем worker ради ручного просмотра.
Встроенный host и браузер не получают новых разрешений или способов обхода guards.
Удалить двойное владение глобальными controls в `app.js`/`updates.js`/оболочке.

Реализация: оболочка создаёт прежние IDs controls и диалога один раз после
подтверждения Windows host и загружает существующий `/updates.js`. Контроллер
обновлений владеет одним локальным polling timer, при pagehide/недоступности
приостанавливается и игнорирует старые ответы. `app.js` больше не создаёт
обработчик выхода и не опрашивает обновления. Отказ завершения показывается
рядом с содержимым, без остановки worker в обход backend. Нажатие выхода сначала
проверяет несохранённые правки; успешный выход уведомляет главную страницу.

### 3. Единые переходы

Одна карта ссылок по среде и один путь выполнения menu navigation. На Windows
одинаковые команды из главной, библиотеки и записи ведут к одинаковым экранам.
Существующие `/output/`, `/create`, `?job=`, `folder`, `report`, `material`,
`stage`, hash и прямые ссылки сохраняются; без принудительного удаления маршрутов.
Контекст записи переносится только там, где это предусмотрено текущим контрактом;
новая запись не должна случайно открывать предыдущую.

Убрать заменённые page-specific переписывания ссылок в `recording.js` и `studio.js`.
Не удалять селекторы/legacy IDs до проверки их потребителей. Сохранить
`mayLeaveQuickReply`, dirty guard iframe/материала, Back/Forward, URL state и
открытие ссылки с Ctrl/Shift/средней кнопкой. Отказ перехода оставляет документ,
ввод и фокус доступными.

Реализация: единая карта Windows/shared web в `desktop-shell.js`; глобальные
ссылки не копируют query исходной страницы. Контекст записи остаётся в её URL
для Back/Forward, но не превращает команду «Записи» в возврат к одной записи.
Обработчик оболочки не дублирует page-specific обработчики. При отказе dirty guard
меню остаётся открытым, focus возвращается на пункт. При подтверждённом переходе
публикуется `desktop-navigation` с ключом команды; существующая главная обновляет
диагностику при открытии настроек. Проверка этого поведения в браузере отложена.

### 4. Подключение всех поверхностей

Основные места: `windows-app/ui/index.html`, `video_descriptor/library.py`,
`assets/create.html`, `assets/speech.html`, `report.py`, генератор справки
в `windows-app/app.py`, общие shell assets и static allowlist в `serve.py`.
Перед изменением каждой области прочитать её scoped инструкции и page override.

Страница предоставляет место для шапки и контекст, но не собственное меню.
Справка сохраняет обычные ссылки возврата без JavaScript. Онлайн-отчёт использует
оболочку доступного сервера; новый переносимый отчёт использует локальные assets,
не обращается к localhost для управления приложением и не требует CDN.
Старые экспортированные файлы остаются неизменными. Embedded-отчёт не создаёт
шапку, дополнительный player или обработчики глобальных команд.

Реализация: `/speech` сохраняет существующий redirect на `/create` с общей шапкой;
отдельная legacy-форма не возвращается в маршруты. Её HTML и обе справочные страницы
синхронизированы с общим shell и skip link;
ссылки возврата справки без JS сохранены. Главная больше не содержит отдельного
меню приложения и update dialog. Библиотека, создание и новые online-отчёты
используют тот же shell. File-отчёт не делает `/health`, не загружает Windows
команды и скрывает глобальные онлайн-меню; embedded полностью пропускает shell.
Старые сохранённые HTML/assets остаются прежними, включая их старую оболочку.

### 5. Ручной просмотр и удаление дублей

Один проход по главным страницам и прямым URL: одинаковые команды, отступы,
версия/подпись приложения, переходы и возврат из справки. Проверить меню мышью
и клавиатурой, Escape, возврат focus после диалогов, узкое окно и длинные подписи.
Отдельно проверить отказ ухода с несохранённой правкой и отсутствие сброса player.
Состояния offline/error и stop guards проверять изолированно, не останавливать
живые задания. Реальный запрос обновления — отдельное явное действие интерфейса.

Удалить только заменённую разметку, listeners и CSS; не добавлять новый слой
скрытых меню или точечные исключения по ID. CSS пересобрать общей командой.
Синхронизировать MASTER, CONTRACTS, page overrides, `docs/architecture-windows.md`,
действующие guides и `docs/development/history.md`; исправить входящие ссылки.

Выполнен [read-only Edge/CDP проход](BOOTSTRAP-REVIEW.md) с блокировкой мутаций:
меню, навигация, справка, размеры шапки, focus, диалоги и отказ ухода с правкой.
Отдельные error/offline/stop сценарии и installed WebView2 остаются в технической
проверке; реальный выход и запрос обновления не выполнялись.

### 6. Техническая проверка и фиксация

Визуальный [Bootstrap-проход](BOOTSTRAP-REVIEW.md) не заменяет этот этап.
На финальном техническом этапе
проверить shell/navigation/update scenarios, keyboard, ошибки, delayed `/health`,
direct entry и guards в offline fixtures. Не заменять baseline ради PASS.

fetch в shell, а также изолированные update fixtures: `/health` теперь обязателен
для появления Windows-команд. Это изменения проверок контракта, не замена baseline.
Добавить регрессии whitelist/idempotence `with_editor_control_roles` и неизменности
сохранённых отчётов, skip-link focus и `.vd-status` для `run-state`.

`test_workspace_view.py`, `scripts/desktop_design_checks.py`,
`scripts/verify-updates-ui.py` и подходящие workspace scenarios; перечень уточнить
по фактически затронутым контрактам. Затем `python scripts/check-fast.py`.
